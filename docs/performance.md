# Производительность: замеры и оптимизации

> Замеры проведены на Linux-стенде `cl1` (22 ядра, без Docker Desktop),
> стек в Docker (2 API-воркера, Kafka, PostgreSQL, consumer, results).
> Методика и цифры — ниже. На macOS с Docker Desktop тот же стек упирался в
> ~12K RPS из-за виртуализации сети, поэтому стенд обязателен.

## Методика

- Нагрузчик — [`loadtest`](../loadtest/main.go) в режиме `-burst` (один опрос,
  максимальная скорость, без профиля).
- Запускается **внутри docker-сети** стенда, чтобы не платить за NAT хоста.
- Каждый запрос идёт с **уникальной подписанной cookie** — дедупликация не
  срезает нагрузку, все голоса доходят до consumer'а.
- Проверка корректности: `results.total == accepted(202)`.
- Каждая точка — 3 прогона, берётся медиана.

### Важная поправка: один клиент упирается в себя

Один нагрузчик при `-c 600` съедает **~8 ядер CPU** и упирается в **~60K RPS** —
это потолок клиента, а не сервера. Проверено двумя способами:

1. Пустой echo-сервер в Docker на macOS давал 11K, наш полный стек — 12K;
2. Два независимых клиента **по 400** дают суммарно больше, чем один клиент по 600
   (36.7K + 36.9K = **73.7K** против 61K).

Поэтому ёмкость измеряется **суммой нескольких клиентов**, каждый из которых
работает ниже своего потолка.

## Итог

| Метрика | Значение |
|---|---|
| Пропускная способность | **~88 000 RPS** (2 клиента × 400) |
| Корректность | **300 000 / 300 000** голосов, 0 потерь |
| Latency p50 / p90 / p99 | ~0.75 мс / ~2 мс / ~5 мс (при умеренной нагрузке) |
| Latency p50 (burst 88K) | ~1.1 мс |
| Ошибки | 0 |

## Где узкое место (pprof, 60K RPS)

| Слой | Доля CPU |
|---|---|
| `net/http` (весь HTTP-стек stdlib) | **76%** |
| — запись ответа (`finishRequest`) | 34% |
| — чтение/парсинг запроса (`readRequest`) | 18% |
| `Syscall6` (сетевые вызовы) | 32% |
| **наш код (`handleVote`)** | **16%** |
| — `httpx.ReadJSON` | 5.8% |
| — `fingerprint` (HMAC+Verify) | 4.4% |

**Вывод: 76% времени — это stdlib `net/http`, а не наш код.** Дальнейшая
оптимизация прикладной логики даёт мало; масштабирование — только добавлением
API-воркеров.

Судя по всему, потолок — **сеть: один TCP-коннект на запрос** (клиент не
переиспользует соединения между опросами), а `Syscall6` + `readMIMEHeader` +
`Header.Clone` — прямые издержки этого. Переход на HTTP/2 или переиспользование
keep-alive дал бы больше, чем правки кода, но это уже про клиент/транспорт.

## Сделанные оптимизации и их эффект

| # | Что | Эффект |
|---|---|---|
| 1 | `ReadJSON`: `json.Decoder`+`DisallowUnknownFields` → `json.Unmarshal` | +3% (58.3K → 60.2K) |
| 2 | `WriteJSON`: `json.Encoder.Encode` → `Marshal`+один `Write`, `Content-Length`; постоянный ответ голоса предвычислен | вместе с №1 → +4-9% |
| 3 | `GOGC=400` для API-воркеров (обмен памяти на пропускную способность) | **+12%** (78K → 87.7K) |

Суммарно: **~58K → ~88K RPS (+50%)**.

### Почему остановились

- Прикладной код — 16% CPU; даже обнулив его, выигрыш ограничен.
- Стенд уже насыщен: `load average ≈ 30` на 22 ядрах, три клиента не влезают.
- Третий клиент при `c=400` дал просадку вместо роста — классический признак
  плато.

Идеи на будущее (не сделаны — вне рамок текущего этапа):
- пул соединений на клиенте / HTTP-2 на сервере;
- шардировать `voteBuffer.mu` по `poll_id` (сейчас общий мьютекс на все опросы);
- вынести HTTP-парсинг заголовков (сейчас `Header.Clone` в stdlib на каждый запрос
  пикается при большой нагрузке).

## Как воспроизвести

```bash
# сборка linux/amd64 + доставка на стенд + перезапуск
./scripts/deploy-cl1.sh cl1

# замер: N клиентов параллельно, суммарный RPS
ssh cl1 'bash ~/highload-poll-backend/scripts/bench-remote.sh 3 12 400 2'

# полный сценарий с проверкой потерь
ssh cl1 'sudo docker run --rm --network hp_default \
  -v ~/highload-poll-backend/bin:/b alpine:3.20 /b/loadtest \
  -duration 90s -polls 5 -poll-duration 20s -votes-per-poll 60000 -c 600 \
  -api-urls http://hp-api-1:8080,http://hp-api2:8080 \
  -admin-url http://hp-results-1:8081 \
  -cookie-secret dev-cookie-secret-change-me -results-timeout 90s'
```

## Замечания по стенду

При подготовке стенда выяснилось:

- **Docker Hub недоступен** (rate limit + корпоративный registry без доступа к
  `library/*`). Образы пришлось тянуть с ноута: `docker pull alpine@sha256:<amd64-digest>`
  → `docker save` → `rsync` → `docker load`.
- **Дефолтный seccomp-профиль Docker 24 несовместим с ядром 6.1**: postgres
  падал с `Operation not permitted` на `initdb`. Решение — `security_opt:
  seccomp=unconfined` в [`docker-compose.server.yml`](../docker-compose.server.yml).
- Данные postgres вынесены в `tmpfs` (named volume на этой ФС не давал писать).
