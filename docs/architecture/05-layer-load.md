# Нагрузка по слоям архитектуры

> Все расчёты — по оптимистичному сценарию с запасом.
> См. [`01-load-estimation.md`](01-load-estimation.md).

## Исходные параметры

| Параметр | Значение |
|---|---|
| Зрителей на опрос | 100M |
| Доля проголосовавших | 5% → 5M голосов |
| Параллельных опросов | 10 |
| Пиковый RPS на опрос | ~333K |
| Суммарный пиковый RPS | ~3.3M |
| Длительность пика | ~60 сек |
| Размер одного голоса | ~37 байт (fingerprint 36B + option_id 1B) |
| Размер Kafka-сообщения (батч 10K голосов) | ~370KB |
| Сообщений на опрос | 500 (5M / 10K) |

## Архитектура (4 слоя)

```
Зритель → [1. API-воркеры] → [2. Kafka] → [3. Consumer'ы] → [4. Сервис результатов (PostgreSQL)]
```

---

## Слой 1: API-воркеры (продьюсеры Kafka)

Принимают HTTP-запросы от зрителей, накапливают **10K голосов по каждому опросу
отдельно**, отправляют батч в Kafka.

Буфер — **по размеру, не по времени**: воркер копит 10K голосов для конкретного
poll_id, затем шлёт одно Kafka-сообщение (~370KB). Количество воркеров не
фиксируется — оно влияет только на время накопления батча, но не на суммарные
цифры.

**Расчёт (не зависит от количества воркеров):**

| Метрика | Расчёт | Значение |
|---|---|---|
| Пиковый RPS на опрос | — | 333K |
| Produce/sec на опрос | 333K / 10K | **33** |
| Produce/sec суммарно (10 опросов) | 33 × 10 | **330** |
| Входящий RPS (суммарно) | 333K × 10 | **3.3M** |
| Входящий трафик (HTTP) | 3.3M × ~500B | ~1.65 GB/s |
| Исходящий трафик к Kafka | 330 × 370KB | **~122 MB/s** |
| С компрессией LZ4 | — | ~60-70 MB/s |
| In-memory буфер на воркер | 10K × 37B × 10 опросов | ~3.7MB |

**Вывод:** API-воркеры — самый нагруженный слой по RPS. 3.3M HTTP-запросов/sec
требуют горизонтального масштабирования (десятки инстансов за балансировщиком).
Буфер 10K голосов даёт эффективный размер Kafka-сообщения (~370KB) и окно
локальной дедупликации. Go справится — goroutine дешёвые, net/http эффективен.

## Слой 2: Kafka

Буфер между API и consumer'ами. Топик `votes`, key = poll_id.

| Метрика | Значение |
|---|---|
| Write throughput | **~122 MB/s** (330 produce/sec × 370KB) |
| С компрессией LZ4 | ~60-70 MB/s |
| Read throughput | ~122 MB/s (consumer читает в том же темпе) |
| Сообщений на опрос | 500 |
| Размер на опрос (без сжатия) | ~185MB (500 × 370KB) |
| Размер на опрос (LZ4) | ~100MB |
| Всего при 10 опросах | ~1.85GB (без сжатия), ~1GB (LZ4) |
| Партиций | по одной на опрос (key = poll_id) |
| Retention | 5 мин (автоудаление после опроса) |

**Незакоммиченный offset на consumer'е:**
- 500 сообщений × 370KB = **~185MB** на consumer'а
- При 10 consumer'ах: ~1.85GB всего
- При падении consumer'а — перечитывание 500 сообщений (~60 сек)
- **Нормально для Kafka** — небольшой объём

**Вывод:** Kafka переваривает 122 MB/s write без проблем. Sequential I/O,
компрессия, batch запись — штатный режим. 1.85GB storage при retention 5 мин —
минимальный footprint.

## Слой 3: Consumer'ы (обработка)

Читают батчи из Kafka, дедуплицируют in-memory, накапливают счётчики.
Не коммитят offset до полного завершения опроса.

| Метрика | Значение |
|---|---|
| Consumer'ов | 10 (по одному на опрос/партицию) |
| Read на consumer | ~12 MB/s (333K голосов/sec) |
| Сообщений/sec на consumer | ~33 (333K / 10K) |
| In-memory map (fingerprint'ы) | **~250MB** на consumer (5M × 50B) |
| In-memory счётчики | минимальные (poll_id + N options) |
| CPU на consumer | ~7% ядра (map insert ~200ns × 333K) |
| Flush в сервис результатов | 1 раз в конце опроса |
| Размер flush | ~100 байт (счётчики) |

**Память — главный ресурс consumer'а:**
- 250MB на опрос — приемлемо для одного Go-процесса.
- При 2-3 опросах на consumer (если партиций больше, чем consumer'ов) — 500-750MB.
- Нужно мониторить, но не критично.

**При падении consumer'а:**
- Offset не закоммичен → перечитывает весь опрос (500 сообщений, ~60 сек).
- In-memory map пустой → пересчитывает.
- Идемпотентный flush → двойного счёта нет.

**Вывод:** Consumer'ы — лёгкий слой. 12 MB/s read, 7% CPU, 250MB RAM.
Узкое место — память (250MB на опрос), но в пределах нормы.

## Слой 4: Сервис результатов (PostgreSQL)

Хранит метаданные опросов и итоговые результаты. Consumer'ы отправляют
результаты после завершения опроса, получают подтверждение, коммитят offset.

| Метрика | Значение |
|---|---|
| Write RPS (flush результатов) | ~0.17 (10 опросов / 60 сек) |
| Размер flush | ~100 байт |
| Read RPS (админка) | низкий (просмотр результатов) |
| Create RPS (создание опросов) | редкий (админка) |
| Таблицы | polls (мета + результаты) |

**Флоу завершения опроса:**
```
1. ends_at прошло → API отклоняет новые голоса (403)
2. Consumer дочитывает остаток из Kafka (grace period ~30 сек)
3. Consumer отправляет результаты в сервис (HTTP/gRPC)
4. Сервис сохраняет в PostgreSQL (идемпотентно: WHERE status != 'completed')
5. Сервис отвечает OK
6. Consumer коммитит offset в Kafka
7. Consumer удаляет in-memory map
```

**Вывод:** Сервис результатов — минимальная нагрузка. ~0.17 RPS write.
PostgreSQL справится легко. Это обычный CRUD-сервис с админкой.

## Сводная таблица

| Слой | RPS | MB/s | RAM | CPU |
|---|---|---|---|---|
| 1. API-воркеры | **3.3M** | 122 (→ Kafka) | низкая (буфер 100мс) | высокий (HTTP) |
| 2. Kafka | 330 produce/sec | **122** write/read | — | низкий (I/O) |
| 3. Consumer'ы | 33 msg/sec × 10 | 12 × 10 | **250MB × 10** | ~7% × 10 |
| 4. PostgreSQL | ~0.17 | ~0 | — | минимальный |

**Узкие места:**
1. **API-воркеры (слой 1)** — 3.3M HTTP RPS. Решение: горизонтальное
   масштабирование, десятки инстансов за LB.
2. **Память consumer'ов (слой 3)** — 250MB на опрос. Решение: мониторинг,
   при необходимости — больше consumer'ов (меньше опросов на каждый).

**Не узкие места:**
- Kafka — 122 MB/s штатный режим.
- PostgreSQL — 0.17 RPS, минимальная нагрузка.
