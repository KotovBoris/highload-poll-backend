                ┌──────────────┼──────────────┐
                ▼              ▼              ▼
┌───────────────────────────────────────────────────────────────────┐

│                                                                   │
│  • GET  /polls/{id}  — страница опроса, выдача cookie             │

### Компоненты

| Компонент | Технология | Роль |
|---|---|---|
| API-воркеры | Go (net/http) | Приём голосов, выдача cookie, буферизация, produce в Kafka |
| Kafka | Kafka (KRaft, без Zookeeper) | Буфер пика, durability, развязка API и consumer |
| Consumer-воркеры | Go (sarama/segmentio) | Дедупликация, подсчёт, flush результатов |
| Сервис результатов | Go + PostgreSQL | Хранение опросов и результатов, админка |

### Стек

- **Go** — язык (вакансия Go, эффективная конкурентность, low latency)
- **Kafka** — буфер пика, append-only лог, durability
- **PostgreSQL** — метаданные и итоговые результаты (мало записей, SQL)
- **Docker Compose** — локальный запуск всех компонентов

## Как мы к этому пришли

### 1. Батчинг на hot path

**Идея:** API-воркеры не пишут каждый голос сразу, а накапливают батч.

**Почему:** при пиковом RPS запись по одному голосу создаст чрезмерную
нагрузку на хранилище. Батчинг сглаживает пик.

**Рассматривали:** буфер по времени (100мс) vs по размеру (10K голосов).
Выбрали **по размеру** — даёт предсказуемый размер Kafka-сообщения (~370KB,
оптимально для Kafka) и не зависит от количества воркеров.

### 2. Kafka как буфер

**Идея:** API-воркеры пишут в Kafka, consumer'ы читают в своём темпе.

**Рассматривали альтернативы:**
- **In-memory буфер в воркере + flush в БД** — проще, но теряем данные при
  падении воркера, нет backpressure.
- **Redis (SADD + INCR) напрямую из API** — проще, но Redis становится точкой
  contention при пиковом RPS, нет durability.

**Почему Kafka:**
- Буферизирует пик (3M+ RPS в течение 60 сек).
- Durability — при падении consumer'а данные не теряются, offset не сдвинется.
- Backpressure — если consumer не успевает, Kafka копится, никто не падает.
- Развязка API и consumer — независимое масштабирование.

### 3. Дедупликация — асинхронная, в consumer'е

**Идея:** не проверять дубликаты на hot path (в API), а дедуплицировать при
обработке в consumer'е.

**Почему не синхронная:**
- Round-robin (простейший балансировщик) размазывает голоси одного
  fingerprint по разным воркерам → локальная дедуп в API не работает.
- Общий стор дедупликации = точка contention при пиковом RPS.
- Синхронная проверка добавляет сетевой round-trip на каждый запрос → рост
  latency.

**Почему асинхронная допустима:**
- Результаты не публичные, не real-time (см. [`02-product-assumptions.md`](02-product-assumptions.md)).
- Зритель не видит результатов → повторный голос можно принять и отбросить
  позже.

### 4. Локальная дедупликация в consumer'е (без Redis)

**Идея:** `key = poll_id` в Kafka → все голоси одного опроса в одной партиции
→ один consumer → in-memory `map[fingerprint]bool`.

**Рассматривали:**
- **Redis как общий стор fingerprint'ов** — точно, но лишний компонент,
  сетевой round-trip на каждый батч, точка отказа.
- **PostgreSQL (UNIQUE + ON CONFLICT)** — медленно для дедупликации, bloat.

**Почему локальная in-memory:**
- O(1) lookup + insert, без сетевых обращений.
- Один consumer справляется с пиковым RPS на опрос (in-memory операции
  дешёвые).
- Нет лишнего компонента (Redis).

**Риск:** при падении consumer'а in-memory map теряется. Решение: consumer не
коммитит offset до конца опроса → при падении перечитывает весь опрос →
идемпотентный flush (двойного счёта нет).

### 5. Consumer не коммитит offset до завершения опроса

**Идея:** consumer копит весь опрос в памяти, flush в конце, коммит в конце.

**Рассматривали:** коммит по батчам (каждые 10K). При падении — перечитывание
только последнего батча. Но in-memory map теряется → дубликаты пройдут.

**Почему коммит в конце:**
- Опрос короткий (~60 сек) — весь объём помещается в памяти (~250MB).
- При падении — полный replay, идемпотентный flush, чисто.
- `max.poll.interval.ms` (5 мин по умолчанию) — 60 сек + grace period
  укладываются.

### 6. Идемпотентный flush

**Идея:** при flush результатов проверять статус опроса — если уже
`completed`, скипать.

**Почему:** при replay (после падения consumer'а) повторный flush не должен
привести к двойному счёту.

```sql
UPDATE polls SET status = 'completed', results = $1
WHERE id = $2 AND status != 'completed';
```

### 7. Одно Kafka-сообщение = батч голосов

**Идея:** сериализовать массив голосов в одно Kafka-сообщение (10K голосов,
~370KB), poll_id один раз.

**Рассматривали:** одно сообщение = один голос (~150 байт).

**Почему батч голосов:**
- 150 байт — слишком мелкое для Kafka (overhead метаданных).
- 370KB — оптимальный размер (1KB-1MB).
- poll_id не дублируется → экономия.
- 500 сообщений на опрос вместо 5M → меньше overhead, эффективнее компрессия.

### 8. Fingerprint: подписанная cookie primary + IP fallback

**Идея:** `fingerprint = raw UUID из подписанной cookie` (если есть) или
`hash(IP)` — без User-Agent.

**Рассматривали:**
- **Только IP (+UA)** — просто, но NAT объединяет устройства (даже домашние).
  UA исключён из ключа: его ротация бесплатна.
- **Только cookie** — точно, но теряем <1% пользователей без cookie.
- **Требовать cookie обязательно** — технически можно, но лишнее ограничение.

**Почему cookie + fallback:**
- Cookie уникальна для каждого устройства, не зависит от NAT.
- Stateless (сервер не хранит выданные cookie, генерация UUID — O(1)).
- Подпись не даёт выдумать UUID, привязка к poll_id не даёт переиспользовать
  cookie другого опроса.
- Fallback спасает голоса пользователей без cookie и построен только по IP —
  иначе ротация UA превращала бы его в бесконечный источник fingerprint'ов.
- Соответствует требованию «базовая дедупликация».

См. [`03-deduplication.md`](03-deduplication.md).

### 9. Завершение опроса

**Проблема:** как consumer'у понять, что опрос завершён и больше голосов не
будет? Нельзя просто ждать «тишины» — другой воркер может дослать голоса с
задержкой.

**Механизм — worker_id в каждом сообщении + "done" аппрувы:**

1. Каждый API-воркер кладёт свой `worker_id` в каждое Kafka-сообщение.
2. Consumer собирает множество всех `worker_id`, от которых были голоса по
   данному `poll_id`.
3. После `ends_at` каждый API-воркер досылает остаток буфера + "done"
   сообщение (`worker_id`, `poll_id`, `"done"`).
4. Consumer ждёт "done" от **каждого** `worker_id` из собранного множества.
5. Получили "done" от всех → flush → commit → очистка.

**Проблема: воркер мог упасть, не дослав "done".**
- Не можем ждать вечно.
- Решение: **порог коммита** (любое из условий):
  - **(a)** Получены "done" от ≥ Y% воркеров (например, 90%).
  - **(b)** Прошло X сообщений по другим `poll_id` подряд без новых по нашему
    (опрос «остыл»).

**Флоу завершения:**
1. `ends_at` прошло → API отклоняет новые голоса (403).
2. Каждый API-воркер досылает остаток буфера + "done" для этого `poll_id`.
3. Consumer собирает "done" от известных `worker_id`.
4. Условие коммита (a или b) → идемпотентный flush → OK от сервиса →
   commit offset → очистка in-memory map.

**Минус (честно):**
- Можем потерять последние голоса от воркера, который упал и не дослал "done".
- Порог Y < 100% → часть голосов может не дойти.
- Это компромисс между бесконечным ожиданием и потерей данных.
- Для опроса (не финансовая транзакция) — допустимо. При необходимости
  механизм можно докрутить (heartbeat воркеров, более умные таймауты).

### 10. Период ребаланса Kafka

Если при rebalance на одного consumer'а упало несколько опросов (например, 3):
- 3 × 250MB = 750MB RAM — приемлемо.
- 3 × (60 сек + 30 сек grace) = до 270 сек обработки (если последовательно).

**Настройки Kafka consumer:**
- `max.poll.interval.ms` = **600000 (10 мин)** — с запасом, чтобы consumer
  не выкинули из группы при обработке нескольких опросов.
- `session.timeout.ms` = 60000 (60 сек) — heartbeat держит сессию.

### 11. Коммит offset непрерывным префиксом по партиции

**Проблема (выявилась при реализации):** в одну партицию может попасть
несколько `poll_id` (если опросов больше, чем партиций, либо при хеш-коллизиях
ключей). Если коммитить offset'ы «завершённых» опросов в отрыве от незавершённых,
то при падении consumer'а перечитается только часть потока — и данные
незавершённого опроса могут быть потеряны (offset уедет за них).

**Решение:** по каждой партиции ведём очередь прочитанных сообщений
`(offset, poll_id)`. Коммитим **непрерывный префикс** очереди: пока голова
очереди принадлежит завершённому опросу (или является нечитаемым сообщением) —
снимаем её и включаем в коммит. Коммитим максимальный offset префикса одним
вызовом. Незавершённый опрос «держит» хвост очереди и не даёт закоммитить
offset'ы за собой.

**Следствие:** после рестарта consumer перечитает ровно незавершённые опросы —
без потери данных и без избыточного replay.

**Требование к сервису результатов:** API-воркеру и consumer'у нужен `ends_at`
опроса. Источник — внутренний эндпоинт `GET /internal/polls/{id}` сервиса
результатов (закрывает пробел «откуда API узнаёт ends_at»).

### 12. Анти-накрутка: подпись cookie + лимит выдачи

**Проблема:** базовая дедупликация была уязвима к накрутке тремя путями:
- зритель мог **выдумать** произвольный UUID и быть «новым избирателем» каждый раз;
- либо **набрать** настоящих cookie пачкой, многократно дёргая `GET /polls/{id}`;
- а fallback `hash(IP+UA)` давал **третью** дыру: ротация UA (бесплатного
  клиентского заголовка) превращала один IP в бесконечный источник fingerprint'ов.

**Решение (уровень 1 — без DDoS-защиты, как и просили):**

1. **HMAC-подпись cookie**, привязанная к `poll_id`:
   `voter_id = <raw-uuid>.<HMAC-SHA256(secret, poll_id ‖ 0x00 ‖ raw)>`.
   Выдуманный UUID или подпись не проходят проверку → уходят в fallback.
   Проверка — O(1), cookie остаётся stateless.
2. **Fallback только по IP** (`sha256(IP)`, без UA). UA — клиентский заголовок,
   его ротация бесплатна, поэтому он не должен давать новых fingerprint'ов.
   Теперь один IP без cookie = ровно один fingerprint.
3. **Лимит выдачи:** не более `MAX_COOKIES_PER_CLIENT` (по умолчанию **1000**)
   cookie на один **IP** в рамках опроса. Ключ — `(poll_id, IP)`, без UA.
   `GET /polls/{id}` при исчерпании лимита **всё равно отдаёт страницу** — просто
   без новой cookie (зритель никогда не упирается в ошибку).

**Почему 1000, а не «одна на IP»:** за одним IP (CGNAT мобильных операторов)
легитимно находятся сотни устройств. Жёсткое «1 на IP» отсекло бы их всех;
1000 покрывает реальный NAT, но одиночный атакующий с одного IP упирается в тот
же предел вместо миллионов голосов.

**Цена:** несколько устройств за одним NAT **без cookie** схлопываются в один
fingerprint. Компенсируется тем, что при щедром лимите cookie получают почти все
легитимные зрители (они же открывают страницу), так что в fallback остаются в
основном атакующие.

**Ограничение:** лимит локальный для процесса. При N API-воркерах за
round-robin фактический лимит = N × 1000.

**Известная особенность:** лимит локальный для процесса, поэтому при N воркерах
за round-robin фактический предел = N × 1000. Общий стор лимита добавил бы
сетевой round-trip на hot path. **Как обеспечить точный лимит при нескольких
воркерах — открытый вопрос**, требующий отдельной проработки; в рамках задания
осознанно оставляем локальный лимит.

**Что осознанно не делаем (вне рамок ТЗ):**
- Защита от ротации IP — только edge-слой (WAF / anti-bot). Ротация UA больше не
  помогает: UA не участвует ни в ключе лимита, ни в fallback.
- Rate limiting как защита от DDoS — отдельный слой, здесь не нужен.
- Отсев аномалий в consumer'е — точка расширения есть (вторая стадия), не реализовано.

### 13. Порядок «батч → done» внутри API-воркера

**Проблема (найдена при ревью реализации).** Решение «отправлять или нет»
изначально принималось ВНЕ мьютекса буфера: `Add()` возвращал готовый батч, а
вызывающий его отправлял уже после разблокировки. Из-за этого `closePoll()` мог
вклиниться ровно между формированием батча и его отправкой, поставить в очередь
«done» и уйти в Kafka раньше батча. Consumer, увидев «done», завершал опрос —
и голоса этого батча терялись, хотя клиент получил `202`.

**Решение:** решение об отправке перенесено ВНУТРЬ мьютекса буфера. И полный
батч (`Add` достиг `batchSize`), и закрытие (`Close`: остаток + «done») только
кладут элемент в очередь `pb.out` опроса под общим мьютексом. Разбирает очередь
отдельная drainer-горутина опроса — строго в порядке добавления. Так «done» не
может обогнать батч, порождённый конкурентным `Add()`.

**Проверка:** регрессионный тест с конкурентными `Add`/`Close` (сумма
отправленных голосов == число принятых, «done» всегда последний) + демонстрация,
что прежняя схема даёт `DATA RACE` под `-race`.

### 14. `CLOSE_GRACE` обязателен при нескольких воркерах

**Проблема (выявлена при попытке выставить `grace=0`).** Кворум «done» считается
по **известным** consumer'у воркерам (`workersSeen`). Воркер, который обслуживал
опрос, но до `ends_at` не набрал полный батч (10K), не отправил ни одного
сообщения — consumer о нём не знает.

При `grace=0` последовательность такая:
1. `ends_at` наступает; воркер A отправляет остаток + «done»;
2. consumer видит `workersSeen={A}` → кворум `1 из 1` → **завершает опрос**,
   сохраняя только голоса A;
3. воркер B отправляет свой остаток + «done» позже; flush упирается в
   идемпотентный `409` → **голоса B потеряны**.

На сценарии с двумя воркерами это давало потерю **~половины** голосов
(2999 принято → 1499 учтено), а один и тот же `poll_id` завершался дважды.

**Вывод:** `CLOSE_GRACE` — не опциональная «страховка», а обязательный механизм
синхронизации при нескольких воркерах. Значение `0` допустимо только при
единственном API-воркере. Локально достаточно `5s`, в проде — ~`30s`.

**Проверка:** контрольный прогон с `grace=5s` дал `599 984 = 599 984` и
`workers_seen=2 workers_done=2` по всем 15 опросам.

## Минусы архитектуры

### Потеря голосов при недоступности Kafka

API-воркер отвечает зрителю «OK» **до** успешной записи в Kafka (retry в фоне).
Если Kafka недоступна всю минуту голосования:
- Все голоса приняты (OK), но не записаны.
- **Голоса потеряны** — мы всем сказали OK, а на самом деле не сохранили.

**Оценка риска:**
- Не репутационный риск — зритель не видит результатов, мы просто не получим
  данные опроса.
- Kafka — отказоустойчивый кластер, недоступность всей минуты маловероятна.

**Фоллбэк на будущее:**
- Запись батчей на диск (WAL / логи) на API-воркерах при недоступности Kafka.
- Восстановление по логам после восстановления Kafka.
- Альтернатива: запись в логи (файлы) — если что, восстановим статистику по
  ним.

## Что стоит сделать иначе в проде: кворум через heartbeat

Раздел 14 показывает, что `CLOSE_GRACE` — это **таймаут-эвристика**, а не
гарантия. Она отвечает на вопрос «сколько ждать неизвестных воркеров», но не
знает, сколько их вообще существует. Итог — два плохих края:

- grace мал → завершаемся рано, теряем голоса поздних воркеров;
- grace велик → результаты висят лишние десятки секунд, а всё равно без гарантии
  (воркер, «проснувшийся» позже grace, потеряется так же).

**Как сделать правильно.** Нужен явный состав кворума, а не догадки по таймауту:

1. API-воркер при старте (или при первом голосе по опросу) **регистрируется** в
   общем сторе — например Redis с TTL. Стор хранит множество активных воркеров
   по данному `poll_id`.
2. Пока воркер жив, он **поддерживает запись heartbeat'ом** (продлевает TTL).
   Пропала запись — воркер считается мёртвым и из кворума исключается.
3. Consumer после `ends_at` ждёт «done» **от всех, кто есть в кворуме**, а не от
   тех, о ком узнал из потока. Условие завершения:
   - пришли «done» от всех членов кворума — flush;
   - либо член кворума пропал по TTL (не шлёт heartbeat) — считаем его
     потерянным и завершаемся без него.
4. Результат: ждём ровно столько, сколько нужно, ни секундой больше, и **точно
   знаем — кого ждать**. Никакой магической паузы.

**Честно про костыльность.** Это тоже не идеал:

- появляется **внешняя зависимость** (Redis) на критичном пути завершения, а её
  недоступность надо как-то обрабатывать (что тогда — ждать? завершаться?);
- heartbeat сам по себе — таймаут-эвристика, только с меньшим окном: «жив»
  определяется по «давно не слышно», а не по факту;
- TTL и частота heartbeat'ов — новые ручки для настройки и новые сценарии отказа
  (пауза GC, сетевой лаг → воркер ложно признан мёртвым).

**Альтернатива без внешнего стора:** воркеры знают друг друга через сам Kafka
(например, consumer group или отдельный служебный топик с реестром воркеров).
Но это усложняет и без того непростую схему.

**Вывод:** в рамках тестового задания осознанно оставляем таймаут `CLOSE_GRACE`
(1s локально, ~30s в проде) как компромисс между простотой и потерями. Для
прод-качества этот узел нужно перепроектировать на явный кворум с heartbeat —
задача отдельного этапа, зафиксирована здесь как известное ограничение.
