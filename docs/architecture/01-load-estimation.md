# Оценка пиковой нагрузки (RPS)

## Входные данные из постановки

| Параметр | Значение | Комментарий |
|---|---|---|
| Зрители на ролик | ~100 млн | Из задачи |
| Длительность ролика | ~1 минута (60 сек) | Окно голосования |
| Каналы | «крупнейшие ТВ-каналы» | Точное число не задано — оцениваем |

## Допущения и их обоснование

### 1. Доля проголосовавших (participation rate, `p`)

Зритель должен заметить QR-код/ссылку на экране, достать телефон, отсканировать
и проголосовать — всё за ~1 минуту. Реалистичные оценки конверсии для ТВ
QR-опросов:

| Сценарий | `p` | Голосов с 100 млн |
|---|---|---|
| Пессимистичный | 0,5 % | 500 тыс. |
| Реалистичный | 1–2 % | 1–2 млн |
| Оптимистичный | 3–5 % | 3–5 млн |

> QR-код на ТВ даёт низкую конверсию (нужно физически достать телефон и
> отсканировать), но наличие прямой ссылки + узнаваемость бренда могут
> повысить участие. Берём **реалистичный диапазон 1–2 %** как базовый.

### 2. Распределение голосов во времени (spike factor, `k`)

Голоса **не распределены равномерно** по 60 секундам. Зрители видят QR-код не
с первой секунды (нужно показать вопрос, озвучить инструкцию), затем следует
всплеск сканирований. Типичный профиль:

```
RPS
 │     ╭───╮  ← пик (зрители отсканировали QR)
 │    ╭╯   ╰╮
 │   ╭╯     ╰╮
 │  ╭╯       ╰───  ← затухание
 │ ╭╯
 │╭╯
 └────────────────────────→ t (сек)
   0   10   20   30   40  60
```

Пик приходится на ~5–20 секунду. Если бы голоса были равномерны, средний RPS =
`голоса / 60`. Из-за концентрации в первой трети ролика пиковый RPS в
**2–4 раза выше** среднего. Берём `k = 3` как базовую оценку.

### 3. Количество параллельных опросов (`M`)

Национальная компания запускает ролики на нескольких федеральных каналах.
Опросы приурочены к рекламным блокам / конкретным тайм-слотам. Полного
совпадения по времени на всех каналах быть не должно, но частичное
пересечение — реально.

| Сценарий | `M` (параллельных опросов) |
|---|---|
| Минимум | 1 |
| Реалистичный пик | 3–5 |
| Агрессивный (праздничный прайм-тайм) | до 10 |

Берём **M = 5** как расчётный пик.

## Расчёт

### Формула

```
RPS_peak_single = (N_viewers × p × k) / T

RPS_peak_total  = RPS_peak_single × M
```

где:
- `N_viewers` = 100 000 000
- `p` — доля проголосовавших
- `k` — spike factor (концентрация во времени)
- `T` = 60 сек
- `M` — число параллельных опросов

### На один опрос

| Сценарий | p | k | Голосов | Средний RPS | **Пиковый RPS** |
|---|---|---|---|---|---|
| Пессимистичный | 0,5 % | 3 | 500 тыс. | ~8,3 тыс. | **~25 тыс.** |
| Реалистичный | 1,5 % | 3 | 1,5 млн | ~25 тыс. | **~75 тыс.** |
| Оптимистичный | 3 % | 3 | 3 млн | ~50 тыс. | **~150 тыс.** |

### Суммарно (M = 5 параллельных опросов)

| Сценарий | **Пиковый RPS (суммарно)** |
|---|---|
| Пессимистичный | ~125 тыс. |
| Реалистичный | **~375 тыс.** |
| Оптимистичный | ~750 тыс. |

## Целевой показатель проектирования

| Параметр | Целевое значение |
|---|---|
| Пиковый RPS (запись голоса) | **~100 тыс.** (минимум), масштабирование до **~500 тыс.** |
| RPS на один опрос | **~75 тыс.** |
| Параллельных опросов | до **5–10** |
| Latency на голосование (p99) | **< 500 мс** (зритель не будет ждать) |
| Длительность пика | ~60 сек на опрос |

> **Вывод:** система должна выдерживать **~100K+ RPS на запись** в пике с
> возможностью горизонтального масштабирования до ~500K. Основная нагрузка —
> короткий всплеск (десятки секунд), что определяет выбор архитектуры:
> stateless-воркеры + быстрое хранилище счётчиков, асинхронная агрегация
> результатов.
