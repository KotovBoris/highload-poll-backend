# Архитектура

## Итоговая архитектура

```
┌─────────────────────────────────────────────────────────────────────┐
│                         Зритель (браузер)                            │
│                    QR-код / ссылка → страница опроса                 │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ HTTP
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│                      Балансировщик (round-robin)                     │
└──────────────────────────────┬──────────────────────────────────────┘
                               │
                ┌──────────────┼──────────────┐
                ▼              ▼              ▼
┌───────────────────────────────────────────────────────────────────┐
│                    API-воркеры (Go, stateless)                     │
│                                                                   │
│  • GET  /polls/{id}  — страница опроса, выдача cookie             │
│  • POST /polls/{id}/vote — принять голос                          │
│                                                                   │
│  Hot path:                                                        │
│    принять → fingerprint (cookie || IP+UA) →                       │
│    in-memory буфер (10K голосов на опрос) →                       │
│    batch produce в Kafka                                          │
│                                                                   │
│  После ends_at: 403 "poll closed"                                 │
│  При переполнении/Kafka timeout: 503                              │
└──────────────────────────────┬────────────────────────────────────┘
                               │ batch produce (10K голосов, ~370KB)
                               ▼
┌───────────────────────────────────────────────────────────────────┐
│                         Kafka (topic: votes)                      │
│                                                                   │
│  • key = poll_id → одна партиция на опрос                         │
│  • одно сообщение = батч 10K голосов (poll_id один раз)           │
│  • компрессия LZ4                                                 │
│  • retention: 5 мин                                               │
└──────────────────────────────┬────────────────────────────────────┘
                               │ consume batch
                               ▼
┌───────────────────────────────────────────────────────────────────┐
│                    Consumer-воркеры (Go)                          │
│                                                                   │
│  • один consumer на партицию (на опрос)                           │
│  • in-memory map[fingerprint]bool — локальная дедупликация        │
│  • in-memory счётчики map[pollID][optionID]int                    │
│  • НЕ коммитит offset до полного завершения опроса                │
│                                                                   │
│  Завершение опроса:                                               │
│    1. ends_at + grace period (дочитать остаток)                   │
│    2. идемпотентный flush результатов в сервис результатов        │
│    3. получить OK от сервиса                                      │
│    4. commit offset                                               │
│    5. очистить in-memory map                                      │
│                                                                   │
│  При падении:                                                     │
│    offset не закоммичен → перечитывает весь опрос →               │
│    идемпотентный flush (двойного счёта нет)                       │
└──────────────────────────────┬────────────────────────────────────┘
                               │ HTTP/gRPC (результаты)
                               ▼
┌───────────────────────────────────────────────────────────────────┐
│              Сервис результатов (Go + PostgreSQL)                 │
│                                                                   │
│  • хранит метаданные опросов и итоговые результаты                │
│  • идемпотентный flush: WHERE status != 'completed'               │
│  • админка:                                                       │
│    - POST /admin/polls — создать опрос                           │
│    - GET  /admin/polls/{id}/results — посмотреть результаты       │
└───────────────────────────────────────────────────────────────────┘
```

### Компоненты

| Компонент | Технология | Роль |
|---|---|---|
| API-воркеры | Go (net/http) | Приём голосов, выдача cookie, буферизация, produce в Kafka |
| Kafka | Kafka (KRaft, без Zookeeper) | Буфер пика, durability, развязка API и consumer |
| Consumer-воркеры | Go (sarama/segmentio) | Дедупликация, подсчёт, flush результатов |
| Сервис результатов | Go + PostgreSQL | Хранение опросов и результатов, админка |

### Стек

- **Go** — язык (вакансия Go, эффективная конкурентность, low latency)
- **Kafka** — буфер пика, append-only лог, durability
- **PostgreSQL** — метаданные и итоговые результаты (мало записей, SQL)
- **Docker Compose** — локальный запуск всех компонентов

## Как мы к этому пришли

### 1. Батчинг на hot path

**Идея:** API-воркеры не пишут каждый голос сразу, а накапливают батч.

**Почему:** при пиковом RPS запись по одному голосу создаст чрезмерную
нагрузку на хранилище. Батчинг сглаживает пик.

**Рассматривали:** буфер по времени (100мс) vs по размеру (10K голосов).
Выбрали **по размеру** — даёт предсказуемый размер Kafka-сообщения (~370KB,
оптимально для Kafka) и не зависит от количества воркеров.

### 2. Kafka как буфер

**Идея:** API-воркеры пишут в Kafka, consumer'ы читают в своём темпе.

**Рассматривали альтернативы:**
- **In-memory буфер в воркере + flush в БД** — проще, но теряем данные при
  падении воркера, нет backpressure.
- **Redis (SADD + INCR) напрямую из API** — проще, но Redis становится точкой
  contention при пиковом RPS, нет durability.

**Почему Kafka:**
- Буферизирует пик (3M+ RPS в течение 60 сек).
- Durability — при падении consumer'а данные не теряются, offset не сдвинется.
- Backpressure — если consumer не успевает, Kafka копится, никто не падает.
- Развязка API и consumer — независимое масштабирование.

### 3. Дедупликация — асинхронная, в consumer'е

**Идея:** не проверять дубликаты на hot path (в API), а дедуплицировать при
обработке в consumer'е.

**Почему не синхронная:**
- Round-robin (простейший балансировщик) размазывает голоси одного
  fingerprint по разным воркерам → локальная дедуп в API не работает.
- Общий стор дедупликации = точка contention при пиковом RPS.
- Синхронная проверка добавляет сетевой round-trip на каждый запрос → рост
  latency.

**Почему асинхронная допустима:**
- Результаты не публичные, не real-time (см. [`02-product-assumptions.md`](02-product-assumptions.md)).
- Зритель не видит результатов → повторный голос можно принять и отбросить
  позже.

### 4. Локальная дедупликация в consumer'е (без Redis)

**Идея:** `key = poll_id` в Kafka → все голоси одного опроса в одной партиции
→ один consumer → in-memory `map[fingerprint]bool`.

**Рассматривали:**
- **Redis как общий стор fingerprint'ов** — точно, но лишний компонент,
  сетевой round-trip на каждый батч, точка отказа.
- **PostgreSQL (UNIQUE + ON CONFLICT)** — медленно для дедупликации, bloat.

**Почему локальная in-memory:**
- O(1) lookup + insert, без сетевых обращений.
- Один consumer справляется с пиковым RPS на опрос (in-memory операции
  дешёвые).
- Нет лишнего компонента (Redis).

**Риск:** при падении consumer'а in-memory map теряется. Решение: consumer не
коммитит offset до конца опроса → при падении перечитывает весь опрос →
идемпотентный flush (двойного счёта нет).

### 5. Consumer не коммитит offset до завершения опроса

**Идея:** consumer копит весь опрос в памяти, flush в конце, коммит в конце.

**Рассматривали:** коммит по батчам (каждые 10K). При падении — перечитывание
только последнего батча. Но in-memory map теряется → дубликаты пройдут.

**Почему коммит в конце:**
- Опрос короткий (~60 сек) — весь объём помещается в памяти (~250MB).
- При падении — полный replay, идемпотентный flush, чисто.
- `max.poll.interval.ms` (5 мин по умолчанию) — 60 сек + grace period
  укладываются.

### 6. Идемпотентный flush

**Идея:** при flush результатов проверять статус опроса — если уже
`completed`, скипать.

**Почему:** при replay (после падения consumer'а) повторный flush не должен
привести к двойному счёту.

```sql
UPDATE polls SET status = 'completed', results = $1
WHERE id = $2 AND status != 'completed';
```

### 7. Одно Kafka-сообщение = батч голосов

**Идея:** сериализовать массив голосов в одно Kafka-сообщение (10K голосов,
~370KB), poll_id один раз.

**Рассматривали:** одно сообщение = один голос (~150 байт).

**Почему батч голосов:**
- 150 байт — слишком мелкое для Kafka (overhead метаданных).
- 370KB — оптимальный размер (1KB-1MB).
- poll_id не дублируется → экономия.
- 500 сообщений на опрос вместо 5M → меньше overhead, эффективнее компрессия.

### 8. Fingerprint: cookie primary + IP+UA fallback

**Идея:** `fingerprint = cookie` (если есть) или `hash(IP + User-Agent)`.

**Рассматривали:**
- **Только IP+UA** — просто, но NAT объединяет устройства (даже домашние).
- **Только cookie** — точно, но теряем <1% пользователей без cookie.
- **Требовать cookie обязательно** — технически можно, но лишнее ограничение.

**Почему cookie + fallback:**
- Cookie уникальна для каждого устройства, не зависит от NAT.
- Stateless (сервер не хранит выданные cookie, генерация UUID — O(1)).
- Fallback спасает голоса пользователей без cookie.
- Соответствует требованию «базовая дедупликация».

См. [`03-deduplication.md`](03-deduplication.md).

### 9. Один общий топик Kafka, key = poll_id

**Идея:** топик `votes`, key = poll_id → голоси одного опроса в одной партиции.

**Рассматривали:** по топику на каждый опрос.

**Почему общий топик:**
- Динамическое создание топиков — антипаттерн.
- Rebalance при создании/удалении топиков — боль.
- key = poll_id даёт нужную локальность (один опрос → одна партиция → один
  consumer → локальная дедупликация).

### 10. Завершение опроса

**Идея:** после `ends_at` + grace period → flush → commit → очистка.

**Как определяем завершение:**
- `ends_at` задаётся при создании опроса.
- После `ends_at` API отклоняет новые голоса (403).
- Grace period (~30 сек) — consumer дочитывает остаток из Kafka.
- Flush результатов → OK от сервиса → commit offset → очистка in-memory.

**Почему grace period, а не точное отслеживание offset per poll_id:**
- Проще, надёжнее.
- При постоянном потоке опросов глобальный lag никогда не 0, но для
  конкретного poll_id сообщения перестают поступать после `ends_at`.
