# Дедупликация и fingerprint

## Требование из задания

> «дедупликация базовая (не слишком защищенную от обхода, достаточную на уровне
> обычных, не технически подкованных пользователей)»

## Стратегия fingerprint

```
fingerprint = raw UUID из ПОДПИСАННОЙ cookie   если подпись валидна для poll_id
fingerprint = hash(IP + User-Agent)            иначе (fallback)
```

### Cookie (primary, подписанная)

- **Что:** серверный UUID-токен, выдаётся при загрузке страницы опроса (GET).
- **Как:** `Set-Cookie: voter_id=<raw-uuid>.<hmac>; SameSite=Lax; HttpOnly`, где
  `hmac = HMAC-SHA256(COOKIE_SECRET, poll_id ‖ 0x00 ‖ raw-uuid)`.
- **Почему подпись:** без неё зритель мог выдумать произвольный UUID и «стать
  новым избирателем» на каждый запрос. Подпись делает такую подделку
  невозможной без знания секрета.
- **Привязка к опросу:** в подпись входит `poll_id`, поэтому cookie, выданная для
  одного опроса, на другом не принимается и уходит в fallback.
- **Stateless:** проверка — один HMAC, O(1), без обращений к хранилищу. Сервер
  не хранит выданные cookie.
- **Слабость:** очищается (инкогнито, ручная очистка, блокировщики). Тогда
  срабатывает fallback.

### Лимит выдачи cookie (анти-накрутка)

Подпись закрывает **подделку** UUID, но не мешает набрать настоящих подписанных
cookie пачкой, многократно дёргая `GET /polls/{id}`. Поэтому выдача ограничена:
**на пару (poll_id, IP+UA) cookie выдаётся один раз**, повторный запрос → `429`.

- Реализация — in-memory LRU+TTL в API-воркере. Запись живёт до `ends_at` опроса
  + запас, объём ограничен.
- **Ограничение:** лимит локальный для процесса. При N воркерах за round-robin
  фактический лимит = N cookie на пару. **В проде** это снимается маршрутизацией
  на балансировщике по ключу: consistent hashing по `poll_id|IP|UA` прибивает
  пару к одному воркеру — тогда лимит точен. Это отмечаем как prod-путь, в
  тестовом задании реализуем in-memory.
- Ротация IP/UA обходит лимит — защита от этого только на edge (WAF/anti-bot),
  вне рамок задания.

### IP + User-Agent (fallback)

- **Что:** хеш (SHA-256) от внешнего IP-адреса + строки User-Agent.
- **Когда:** cookie отсутствует или не принята.
- **Почему хэш:** строка `IP + User-Agent` переменной длины (User-Agent до ~500
  символов). Хэш даёт фиксированную длину (32 байта), компактность в памяти и
  единый формат ключа.
- **Почему fallback:** менее точен (NAT объединяет устройства), но для
  домашних зрителей (большинство) — достаточно. Один IP + один браузер =
  один fingerprint.
- **Слабость:** NAT (несколько устройств за одним IP → ложноположительная
  дедупликация). Для корпоративных сетей — проблема, но ТВ-зрители в основном
  дома, за личным роутером, с разными User-Agent.

## Когда выдавать cookie

При загрузке страницы опроса (GET `/polls/{id}`):
1. Клиент открывает страницу → сервер отдаёт HTML + `Set-Cookie`.
2. Браузер сохраняет cookie.
3. При голосовании (POST) cookie уже есть → используется как fingerprint.

## Дедупликация — асинхронная

См. [`02-product-assumptions.md`](02-product-assumptions.md), допущение 3.

- Hot path: принять голос → записать в буфер → ответить «OK». Без проверки
  дедупликации в моменте.
- Дедупликация: при flush батча — проверить fingerprint'ы против множества
  уже проголосовавших. Дубликаты отбросить, новые — учесть.

## Сценарии

| Сценарий | IP | Cookie | Fingerprint | Результат |
|---|---|---|---|---|
| 2 устройства дома | одинаковый | разные | разные | оба голосуют ✅ |
| 1000 устройств за NAT | одинаковый | разные | разные | все голосуют ✅ |
| 1 устройство, повтор | одинаковый | одинаковая | одинаковый | повтор отклонён ✅ |
| Очистил cookie, повтор | одинаковый | нет → fallback | одинаковый (IP+UA) | повтор отклонён ✅ |
| Инкогнито, повтор | одинаковый | нет → fallback | одинаковый (IP+UA) | повтор отклонён ✅ |
| VPN (разные IP) | разный | нет | разные | обход (допустимо) ⚠️ |
| 2 устройства, один браузер | одинаковый | нет → fallback | одинаковый (IP+UA) | 2-й отклонён (погрешность) ⚠️ |

## Осознанные допущения

- 2 устройства с одним браузером за одним NAT → 2-й голос отклонён (редкий
  случай, погрешность минимальна). Лимит выдачи cookie усиливает это: 2-е
  устройство за тем же NAT с тем же UA не получит cookie вовсе.
- Очистка cookie → сработает fallback IP+UA, повторный голос с того же IP+UA
  будет отброшен при дедупликации. Валидную cookie заново получить с того же
  IP+UA нельзя (лимит выдачи).
- VPN/прокси + ротация UA → обход (задача не требует полной защиты от этого;
  в проде — edge-слой).
- Cookie — «strictly necessary» (функциональный токен, не трекинг), не требует
  consent banner по GDPR / 152-ФЗ для анонимного опроса. HMAC-подпись не меняет
  этой характеристики: содержимое cookie не трекает пользователя между сайтами.
