# Спека: API-воркер (api)

> Источник истины по контрактам. Интеграционные тесты и реализация должны
> соответствовать этой спеке.

## Назначение

API-воркер — stateless hot-path сервис: принимает голоса зрителей, выдаёт cookie,
буферизует голоса (10K на опрос) и асинхронно отправляет батчи в Kafka. После
`ends_at` отклоняет голоса и досылает «done».

Ключевой принцип: **зритель получает ответ до записи в Kafka**. Produce идёт в
фоне с retry «до посинения» (см. архитектуру, раздел «Минусы»).

## Транспорт

- HTTP/1.1, `net/http`, JSON.
- Порт по умолчанию: **8080** (`HTTP_ADDR`, например `:8080`).

## Модель fingerprint и защита от накрутки

```
fingerprint = raw UUID из ПОДПИСАННОЙ cookie   если подпись валидна для poll_id
fingerprint = sha256(IP)                       иначе (fallback)
```

IP берётся из `X-Forwarded-For` → `X-Real-IP` → `RemoteAddr`.
Реализация: [`internal/fingerprint`](../internal/fingerprint/fingerprint.go:1).

> **Почему fallback только по IP, без User-Agent.** UA — клиентский заголовок,
> его ротация бесплатна. Пока fallback был `sha256(IP+UA)`, атакующий слал
> `UA: bot-1, bot-2, …` и каждый раз получал новый fingerprint — накрутка с одного
> IP была неограниченной. Без UA один IP без cookie даёт ровно один fingerprint.
> Цена: несколько устройств за одним NAT без cookie схлопываются — осознанный
> компромисс (см. ниже).

### Подпись cookie (HMAC)

Cookie выдаётся в формате `"<raw-uuid>.<hex HMAC-SHA256(secret, poll_id ‖ 0x00 ‖ raw)>"`.

- Подпись привязана к **конкретному опросу**: cookie, выданная для одного опроса,
  на другом не проходит проверку и уходит в fallback.
- Подделать подпись без секрета нельзя (сравнение в постоянном времени).
- Проверка — O(1), без обращений к хранилищу: cookie остаётся stateless.
- Секрет — `COOKIE_SECRET`. Пустой → случайный (куки не выживают рестарт; только dev).

### Лимит выдачи cookie (анти-накрутка)

Подпись закрывает **подделку** идентификатора, но не мешает набрать настоящих
подписанных cookie пачкой. Поэтому выдача ограничена: на один **IP** в рамках
опроса можно выдать не более `MAX_COOKIES_PER_CLIENT` cookie (по умолчанию 1000).

- Ключ лимита — **(poll_id, IP)**. UA в ключ не входит.
- Значение 1000 рассчитано на CGNAT мобильных операторов (сотни устройств за IP):
  реальный NAT получает свои cookie, а одиночный атакующий с одного IP упирается
  в тот же предел вместо миллионов.
- Реализация — in-memory счётчик с TTL ([`internal/api/issued.go`](../internal/api/issued.go:1)),
  записи живут до `ends_at` опроса + запас, объём ограничен `MAX_ISSUED_ENTRIES`.
- **`GET /polls/{id}` никогда не отвечает ошибкой из-за лимита.** При исчерпании
  лимита страница отдаётся без новой cookie, и голос зрителя уходит в fallback.
- Если cookie уже есть у клиента — новых не выдаётся (лимит не расходуется).

**Осознанные ограничения:**

- Лимит **локальный для процесса**: при N API-воркерах за round-robin фактический
  лимит = N × maxCookies. В проде это снимается маршрутизацией на балансировщике
  по ключу (consistent hashing по `poll_id|IP`) — тогда все запросы IP идут на
  один воркер и лимит точен. См. [`docs/architecture/04-architecture.md`](../docs/architecture/04-architecture.md).
- Ротация IP обходит лимит — от этого защищает только edge-слой (WAF/anti-bot),
  вне рамок ТЗ. Ротация UA больше не помогает (UA не участвует ни в ключе лимита,
  ни в fallback).
- `DISABLE_ISSUE_LIMIT=true` выключает лимит (используется нагрузочным тестом).

## Публичные ручки

### `GET /polls/{id}` — страница опроса

Назначение: отдать метаданные опроса и **выдать подписанную cookie** `voter_id`.

- Сервер берёт метаданные из сервиса результатов
  (`GET /internal/polls/{id}`), кэширует.
- Если в запросе нет cookie `voter_id` — генерирует UUIDv4, подписывает его для
  этого `poll_id` и ставит
  `Set-Cookie: voter_id=<uuid>.<hmac>; Path=/; Max-Age=86400; SameSite=Lax; HttpOnly`.
  Если cookie уже есть — повторно не выдаёт (не перезаписывает).
- Выдача ограничена: не более `MAX_COOKIES_PER_CLIENT` cookie на один IP в
  рамках опроса. При исчерпании лимита страница отдаётся **без** новой cookie
  (никогда не ошибкой) — см. раздел о лимите выше.
- В ответе **нет** результатов опроса (результаты не публичные).

Ответ: `200 OK`, [`model.Poll`](../internal/model/model.go:1) (без `results`).

```json
{
  "id": "3f2b...",
  "question": "...",
  "options": [{"id": 1, "text": "Красный"}],
  "status": "active",
  "created_at": "...",
  "ends_at": "2026-09-10T08:01:00Z"
}
```

Ошибки: `404 not_found` — опроса нет; `503 unavailable` — сервис результатов
недоступен и нет кэша.

### `POST /polls/{id}/vote` — принять голос

Тело: `{"option_id": 1}` ([`model.VoteRequest`](../internal/model/model.go:1)).

Алгоритм:

1. Получить метаданные опроса (из кэша / сервиса результатов).
   Нет опроса → `404 not_found`.
2. Валидировать `option_id` — должен быть среди `options`.
   Иначе → `400 bad_request`.
3. Проверить время: `now` vs `ends_at`.
   - Если `now >= ends_at` → `403` c `{"error":"poll_closed"}`; при первом
     срабатывании инициировать закрытие опроса (флаш остатка + «done»).
4. Иначе: вычислить fingerprint, добавить голос в буфер, ответить `202 Accepted`.

Ответ: `202 Accepted`

```json
{ "status": "accepted" }
```

| Код | Условие |
|---|---|
| `202` | Голос принят в буфер |
| `400` | Невалидный JSON / `option_id` отсутствует или не входит в опции |
| `403` | Опрос закрыт (`now >= ends_at`) — `poll_closed` |
| `404` | Опрос не найден |
| `503` | Не удалось получить метаданные опроса (сервис результатов недоступен, кэша нет) |

### `GET /healthz`

`200 {"status":"ok"}` — процесс жив.

## Буферизация и отправка в Kafka

- Буфер — **на каждый `poll_id` отдельно**, лимит `VOTE_BATCH_SIZE` (10K).
- При достижении лимита буфер целиком превращается в один
  [`model.VoteBatch`](../internal/model/model.go:1) и ставится в очередь отправки;
  буфер очищается.
- Отправка — **асинхронная**: пул фоновых воркеров читает очередь и вызывает
  `Producer.Produce` с бесконечным retry (backoff). Ошибка produce не влияет на
  HTTP-ответ зрителю.
- **Порядок в пределах опроса гарантирован:** очередь шардируется по `poll_id`
  (FNV-хеш → номер воркера), поэтому все батчи одного опроса обрабатываются одним
  воркером и уходят в Kafka в порядке постановки. Это критично — «done» не должен
  обогнать остаток голосов, иначе consumer завершит опрос, недосчитав голоса.
  Параллелизм между разными опросами сохраняется.
- Каждый батч несёт `worker_id` воркера (UUID, генерируется при старте).

## Завершение опроса (сторона воркера)

Два триггера закрытия опроса:

1. **По запросу:** голос пришёл после `ends_at` → `403` + закрытие.
2. **Фоном:** watcher периодически (`CLOSE_CHECK_INTERVAL`) обходит активные
   опросы и закрывает те, у которых `now >= ends_at` (даже если трафика нет).

Закрытие (идемпотентно, ровно один раз на poll_id):

1. Пометить буфер опроса как `closed` (новые голоса по нему больше не буферизуются).
2. Поставить в очередь **остаток буфера** (если непуст) как обычный батч.
3. Поставить в очередь **«done»-сообщение**:
   `{"poll_id":..., "worker_id":..., "done":true}`.
4. По прошествии `POLL_CACHE_TTL` после закрытия — удалить опрос из кэша.

## Кэш метаданных опроса

- `poll_id → poll` с TTL `POLL_CACHE_TTL` (по умолчанию 1m).
- Кэш потокобезопасен. При промахе — синхронный запрос в сервис результатов.
- Одинаковые одновременные промахи схлопываются (single-flight), чтобы не
  устраивать «thundering herd» на сервис результатов.

## Требования к корректности и производительности

- Hot path — **O(1)**: чтение кэша + append в буфер под мьютексом; I/O в Kafka
  вне hot path. Целевой p99 на `POST /vote` при попадании в кэш — **< 10 ms**
  (локальный тест), архитектурная цель p99 < 500 ms.
- **Ключ партиционирования** = `poll_id` (обеспечивает one-consumer-per-poll).
- **Ровно один «done» на (poll_id, worker_id)** — гарантия завершения.
- При недоступности Kafka голоса буферизуются/ставятся в очередь, но
  **могут быть потеряны** при переполнении очереди или падении воркера —
  осознанный компромисс (см. архитектуру).
- Гонки буфера и закрытия опроса — строго под мьютексом; тест на гонки
  (`-race`) обязателен.
- **Инвариант порядка:** для одного `poll_id` сообщение «done» строго следует за
  всеми батчами голосов этого опроса. Нарушение ведёт к потере хвостовых голосов
  (consumer завершит опрос по «done» до прихода остатка).

## Зависимости и точки мокирования (для интеграционных тестов)

```go
// Отправка батчей в Kafka.
type Producer interface { // internal/kafka.Producer
    Produce(ctx context.Context, batch model.VoteBatch) error
    Close() error
}

// Получение метаданных и flush (API-воркер использует только GetPoll).
type ResultsClient interface { // subset of internal/resultsclient.Client
    GetPoll(ctx context.Context, id string) (model.Poll, error)
    FlushResults(ctx context.Context, id string, r model.Results) (bool, error)
}
```

- Интеграционные тесты поднимают HTTP-сервер воркера (`httptest`) с
  **фейковым Producer** (пишет вызовы в память) и **фейковым ResultsClient**.
- Ключевые проверки: выдача cookie, fingerprint cookie/fallback, `202/400/403/404`,
  формирование батча по достижении `VOTE_BATCH_SIZE`, «done» после закрытия,
  отсутствие «done» раньше времени, потокобезопасность.
